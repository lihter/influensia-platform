01 · Your four answers, and the two conflicts they created

What was decided today and what it collides with

Answer (22 Sep)Consequence
First client: agency modeThey pay the factory price plus our fee. The invoice must show two numbers. Whether they wire the factory or wire us decides whether the factory is disclosed on their order — see the conflict below.
English only, strings externalisedOne messages file from day one; Polish is a translation job later, not a rewrite.
WhatsApp: status onlyThe platform must make status questions unnecessary on its own — milestones, ETAs, actions and documents have to be complete, because there is no chat to fall back on. See the second conflict.
Sheet import: live lines + all suppliersAn import script is part of week 4; the mapping is in section 09.

Conflict 1 — agency mode vs "the client never sees the factory"

If the client wires the deposit to the factory's bank account, the factory's registered name is on their bank statement on day one; no amount of front-end code hides it. Resolution taken (D-10): agency with pass-through payments — the client wires factory price + fee to us, we pay the factory. The fee is visible, the factory is not. If the client insists on paying the factory directly, the platform records agency_direct and stops pretending; anonymity then holds only in the catalog.

Conflict 2 — "status only" vs "never messaged on WhatsApp again"

Status-only means conversations stay on WhatsApp, so the platform cannot stop all messages — only the ones that ask where is my order, when does it arrive, what do you need from me. Those are the majority and they are killed by milestones + ETAs + an actions queue + email on every change. Resolution taken (D-08): no chat in v1, but every order has an Updates feed the agent writes to, an "ask about this order" box that emails the agent and lands on the timeline, and a way for agents to log a WhatsApp exchange onto the order — so the record is complete even though the channel is not. If status questions keep arriving after four weeks, in-app messaging is the first v1.1 item.

02 · Principles

Six rules the decisions follow

  • Same effort as WhatsApp for the client. A new request is a pasted link and a quantity. Everything else is our job.
  • Actions first. The first thing a client sees is what is waiting on them; the first thing an agent sees is what is stale or waiting on us.
  • One page per order that holds everything. Milestone, ETA, money, documents, updates, history of the same product. Agents and clients look at the same object, with different fields.
  • The factory is invisible by construction. Client code paths cannot reach supplier tables; publishing anything to a client is an explicit action that runs a leak check.
  • Foundation for many clients, UI for one. Organisations, memberships, roles and audit exist in the schema from day one; the client never sees the word "organisation".
  • Boring, current, hosted. Next.js 16, Postgres, one ORM, one auth library, one email provider, no queue vendor, no self-hosting. Fewer moving parts than the automation stack already planned.

07 · Anonymity in code

Nine mechanisms, one test that must never be skipped

Build-time

  • 1 · Import boundarysrc/server/client/** may import db/schema/app only; an ESLint no-restricted-imports rule forbids db/schema/supplier there, and app/(client)/** may import only server/client.
  • 2 · DTOs are allowlistsEvery client-facing shape is a zod schema built with .pick() and .strict(); no select *, no spreading rows into responses.
  • 3 · Key denylist testA Vitest test walks every client DTO schema and fails on any key matching /supplier|factory_id|participation|contact|wechat|alibaba|1688|uscc|quote|po_/.
  • 4 · Server-only idsparticipation_id, po_id, supplier_id are typed as server-only fields and excluded from every serialiser by construction.

Run-time

  • 5 · Files by prefixThe client download endpoint signs keys under …/client/… only. Agents upload to …/internal/…; "Publish to client" copies the object after the leak check and flips documents.visibility.
  • 6 · Leak checkOn every publish and every client-visible comment: scan filename, text and PDF text layer for supplier names from the DB, Alibaba/1688 URLs, WeChat handles, +86 numbers, company suffixes (Co., Ltd / 有限公司). Block with a reason.
  • 7 · ImagesRe-encoded server-side (EXIF gone); only kind=clean images serialise to clients; supplier originals keep kind=supplier_facing.
  • 8 · Factory range labelFactory F-0042 comes from a sequence, not from the supplier; the DTO is {label, items[]}; the PDF is the sanitised upload only.
  • 9 · Anonymity crawlPlaywright logs in as the seeded client, visits every client page and API route for an order whose supplier is named ZZLEAKTEST Co., Ltd., and fails on any occurrence. Runs on every PR.

v1.1 hardening: a Postgres role app_client with no privileges on the supplier schema, used by the client request path — defence in depth in case a future refactor breaks rule 1.

08 · UX

Three screens carry the product

Client flows

  • First loginInvite email → set password → dashboard with an empty "Waiting on you" and a "New request" button. No onboarding tour.
  • New requestPaste links / drop photos → quantities → send. Confirmation email with the REQ reference. Agent questions arrive as an Update + email, answered via "Ask about this order".
  • Price readyEmail → offer page: options A/B/C, price ladder, MOQ, lead time, deviations in plain words, sample cost → Accept · Ask for changes · Decline.
  • SampleEmail when shipped with tracking; approve or reject with photos.
  • Order confirmedInvoice (factory price + fee for this client), amounts due; upload artwork; see approval.
  • Production → deliveryETA changes emailed; QC result with report; shipping documents; confirm delivery; Reorder button.

Agent flows

  • Ops dashboardStale lines (no change in 5 working days), waiting-on-us, waiting-on-client, unassigned. Claim with one click.
  • Request lineComplete the spec → freeze (v1) → cost model draft (Claude) → target price → generate RFQ → sourcing board.
  • Sourcing boardAdd suppliers from the DB or inline; log quotes (form or file upload → extraction); shortlist with reasons; negotiate; Build offer picks the options and hides the rest.
  • OrderConfirm → PI → payments → artwork approval → PO per supplier → production ETA → inspection upload → shipment → done. Every step writes the timeline and, where mapped, emails the client.
  • Log WhatsAppPaste a message or screenshot onto the order; it shows on the timeline with source = WhatsApp so the record stays complete.
  • Factory rangeUpload the sanitised PDF, enter items, publish to the client under "Factory F-nnnn".
